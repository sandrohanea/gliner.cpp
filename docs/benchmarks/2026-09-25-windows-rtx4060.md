# Windows CPU/CUDA benchmark: Core i7-13800H and RTX 4060 Laptop

**Date:** 2026-09-25. **Source:** benchmark JSON supplied by the user from the same Windows machine. These tables summarize those existing runs; no measurements were rerun to create this report. Original JSON logs are not included here.

## Summary

C++ CUDA reduced mean latency by **14.17x for joint questions** and **16.42x for separate questions** versus C++ CPU. Python/PyTorch was faster on average than the current C++ runtime on both CPU and CUDA for this workload. C++ CUDA had a lower joint-mode p95 than Python CUDA.

This is a short, repeated two-question workload with 20 measured requests per mode. It does not establish a universal performance ranking. Metal results belong in a separate report from the Apple device and are not inferred here.

A request answers **both questions**. Separate-mode latency is the total for both sequential calls, not latency per question. C++ joint mode reuses one state; separate mode reuses two states sharing the same model. Python has no equivalent explicit state allocator.

Joint schemas attend to one another. Their logits can differ from separate-call logits even when both implementations are correct.

### Precision and timing

Both CUDA runs used:

```text
NVIDIA_TF32_OVERRIDE=0
GGML_CUDA_CUBLAS_COMPUTE_TYPE=f32
```

C++ additionally uses the generated GGML source fix that bypasses the small-matrix TF32 path when F32 activation inputs are requested. Python reports `float32_matmul_precision=highest`, `cuda_matmul_allow_tf32=false` and `cudnn_allow_tf32=false`.

C++ public inference calls synchronize the backend. Python calls `torch.cuda.synchronize` before and after each CUDA request's timing window. Timed work includes preprocessing, encoder execution, label-state extraction, classification and result materialization/transfers. Model loading, file reading, warmup, validation and JSON formatting are excluded.

Percentiles use linear interpolation at `(n - 1) * p`. Throughput is calculated as `1000 / mean_latency_ms`; questions/sec is twice requests/sec.

## Loading and first requests

| Implementation | Model load (ms) | First joint request (ms) | First separate request (ms) |
|---|---:|---:|---:|
| C++ CPU | 2163.67 | 498.43 | 872.05 |
| Python CPU | 336.08 | 493.30 | 477.32 |
| C++ CUDA | 4039.63 | 103.79 | 58.62 |
| Python CUDA | 3116.76 | 284.02 | 118.69 |

**Do not interpret these load-time differences as equivalent application-startup speedups.** The Python helper excludes imports and loads only the processor, encoder and classifier. Safetensors can map data lazily; the C++ loader reads the GGUF payload and copies the required model weights. First requests may include lazy page faults, graph/scratch allocation and kernel initialization.

Joint mode runs before separate mode. The first separate request therefore benefits from an already initialized process/backend and is not a fresh-process cold start. Neither run controls the OS file cache.

## Correctness evidence

The benchmark reports have identical task definitions, token counts and F32 settings. Comparing the final CUDA logits in the two reports gives maximum absolute differences of:

| Mode | C++ CUDA versus Python CUDA |
|---|---:|
| Joint | `1.6689300537109375e-6` |
| Separate | `2.384185791015625e-6` |

The CPU reports also agree within the established F32 logit tolerance. Joint results must be compared to joint results, and separate results to separate results.

Separately, the user reported all 13 real-checkpoint C++ CUDA parity cases passing against the Python CPU oracle, including all 25 hidden-state outputs per case, with the unchanged `atol=rtol=3e-4`. The maximum absolute hidden-state error in that suite was `0.00010967255`. All three expanded CUDA CTest tests also passed. That suite is distinct from this single-input performance comparison; matching benchmark logits is not a substitute for intermediate-layer checks on Python CUDA.

## Reproduce the workload

Build the CPU and CUDA executables and prepare the Python environments as described in the [main README](../../README.md#performance-benchmark). Use an approved CUDA-enabled PyTorch wheel for the Python CUDA environment.

Run sequentially on the same machine, with builds and unrelated workloads stopped:

```powershell
$workload = @(
  "--text", "Please refund my order; the delivery was late.",
  "--task", "intent", "--labels", "refund_request,order_status,other",
  "--task", "sentiment", "--labels", "positive,neutral,negative",
  "--threads", "4", "--mode", "both", "--warmup", "3", "--iterations", "20"
)

$env:NVIDIA_TF32_OVERRIDE = "0"
$env:GGML_CUDA_CUBLAS_COMPUTE_TYPE = "f32"

.\build-cpu\Release\gliner-bench.exe --model .\models\decide.gguf @workload `
  > .\build-cpu\bench-cpu.json

.\build-cuda\Release\gliner-bench.exe --model .\models\decide.gguf @workload `
  > .\build-cuda\bench-cuda.json

.\build-oracle\Scripts\python.exe .\tests\bench_python.py `
  --checkpoint .\models\GLiNER2.5-Decide --device cpu @workload `
  > .\build-oracle\bench-python-cpu.json

.\build-oracle-cuda\Scripts\python.exe .\tests\bench_python.py `
  --checkpoint .\models\GLiNER2.5-Decide --device cuda @workload `
  > .\build-oracle-cuda\bench-python-cuda.json
```

The resulting JSON includes individual samples and final logits. Keep those files when publishing follow-up runs, together with `git rev-parse HEAD`, `git -C ggml rev-parse HEAD`, compiler/driver versions and the input arguments.

## Interpretation and limits

- PyTorch's native kernels are faster on average than this implementation for the supplied workload. The result is not evidence that Python language overhead is negligible in every application, or that GGML is slower on every model.
- PyTorch CPU uses MKL/oneDNN and an upstream tokenizer cache. C++ currently does not cache schema/text tokenization. These are possible contributors, not measured bottlenecks.
- The CUDA stacks differ: PyTorch bundles runtime 12.6, whereas C++ was built with toolkit 13.4. No attribution of the gap to that version difference has been established.
- The runs were taken at different times. Laptop power/thermal state, background activity and CPU affinity were not captured. Twenty samples of one short repeated input are insufficient for general throughput or p95 claims.
- Peak RAM/VRAM, sustained thermal behavior, concurrent requests, longer contexts, other GPUs and real-checkpoint F16 performance were not measured here. Model file size is not resident or peak memory.
- Next steps are longer isolated runs and profiling of graph construction, tokenization, matrix kernels/launches and transfers, preserving the current F32 precision settings and parity tolerances.
