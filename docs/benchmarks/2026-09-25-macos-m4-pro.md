# macOS CPU/Metal benchmark: Apple M4 Pro

**Date:** 2026-09-25. **Source:** benchmark JSON measured on this Mac from the local checkout before merging the Windows report. The three runs were sequential. Their JSON files remain in ignored local build directories and are not part of this report.

## Summary

With the F32 precision overlay, C++ Metal reduced mean latency by **2.33x for joint questions** and **2.55x for separate questions** versus C++ CPU. Python/PyTorch CPU was faster on average than C++ CPU and patched Metal for this workload. The runs used the same text, ordered tasks and F32 checkpoint; their final logits agree closely. A later experiment without the Metal precision changes was much faster but failed the synthetic F32 parity test, as detailed below.

This is a short, repeated two-question workload with 20 measured requests per mode. It does not establish a universal performance ranking or isolate the effect of connecting the charger: the prior Mac benchmark used a different three-task input.

A request answers **both questions**. Separate-mode latency is the total for both sequential calls. C++ joint mode reuses one state; separate mode reuses two states sharing the model. Python has no equivalent explicit state allocator. Joint schemas attend to one another, so their logits can differ from separate-call logits.

### Precision and timing

The Metal build used the F32 precision overlay described in the [main README](../../README.md). It routes F32 matrix products requesting F32 accumulation away from GGML's shader that narrows both operands to F16. The C++ public inference calls synchronize the backend; Python CPU execution is synchronous. CUDA precision variables were unset in all three reports.

Timed work includes preprocessing, encoder execution, label-state extraction, classification and result materialization/transfers. Model loading, file reading, warmup, validation and JSON formatting are excluded. Percentiles use linear interpolation at `(n - 1) * p`. Throughput is `1000 / mean_latency_ms`; questions/sec is twice requests/sec.

### Without the Metal precision changes

Two separate Release builds on the same M4 Pro used stock GGML Metal dispatch. One retained GLiNER's F32 graph precision requests; the full pre-fix build also restored the graph code from the repository commit, removing those requests. Both used the same GGML v0.24.0 checkout, model, task order and benchmark arguments, with 20 measured requests per mode on AC power. The patched result above was captured earlier, so these are sequential measurements rather than an interleaved controlled comparison.

| Metal configuration | Mode | Mean (ms) | Median (ms) | p95 (ms) | Requests/sec |
|---|---|---:|---:|---:|---:|
| F32 precision overlay | Joint | 215.92 | 215.57 | 218.50 | 4.63 |
| Stock GGML, F32 graph requests | Joint | 39.27 | 39.36 | 39.67 | 25.47 |
| Full pre-fix configuration | Joint | 36.85 | 36.75 | 37.26 | 27.14 |
| F32 precision overlay | Separate | 343.76 | 343.10 | 348.04 | 2.91 |
| Stock GGML, F32 graph requests | Separate | 65.12 | 65.09 | 65.88 | 15.36 |
| Full pre-fix configuration | Separate | 61.08 | 61.01 | 61.56 | 16.37 |

The full pre-fix configuration was **5.86x faster for joint** and **5.63x for separate** requests by mean latency than the patched build. Both stock-dispatch configurations produced identical final logits, differing from the patched build by at most `2.52e-4` joint and `2.98e-4` separate on this input. However, both failed the existing synthetic conversion parity test at F32 fixture 6, encoder layer 1, index 8: absolute error `9.9003315e-5` exceeded the allowed `9.4971475e-5`. Neither satisfies the project's F32 parity requirement. Their builds and full benchmark JSON are retained in ignored `build-metal-unpatched/` and `build-metal-prepatch/` locally. The latter's first model load included about 14 seconds of Metal shader compilation, so its load time should not be compared with the warmed patched build.

New builds can select the full fast configuration with `-DGLINER_METAL_STRICT_F32=OFF`; the default `ON` keeps the validated precision fix. This option was added after the measurements above. Current benchmark JSON records the selected `metal_precision_mode`.

A subsequent 20-sample run using that CMake option averaged **38.94 ms joint** (median 38.95, p95 39.41) and **65.41 ms separate** (median 66.33, p95 67.40). It produced exactly the same final logits as the earlier full pre-fix build. The small timing difference illustrates run-to-run variation; the patched and fast runs were not interleaved.

## Loading and first requests

| Implementation | Model load (ms) | First joint request (ms) | First separate request (ms) |
|---|---:|---:|---:|
| C++ CPU | 520.48 | 522.37 | 877.29 |
| Python CPU | 210.65 | 1074.96 | 258.71 |
| C++ Metal | 573.24 | 232.16 | 348.55 |

The Python helper excludes imports and loads only the processor, encoder and classifier. Safetensors can map data lazily; the C++ loader reads GGUF and copies weights. First requests can include lazy page faults, graph/scratch allocation and kernel initialization. Loader timings therefore do not measure equivalent application startup. Separate mode follows joint mode in each process and benefits from initialized caches. OS file caching was not controlled.

## Correctness evidence

The benchmark outputs have identical task definitions and token counts. Maximum absolute differences in final logits relative to C++ CPU were:

| Mode | C++ Metal | Python CPU |
|---|---:|---:|
| Joint | `1.430511474609375e-6` | `2.86102294921875e-6` |
| Separate | `2.1457672119140625e-6` | `4.0531158447265625e-6` |

These checks compare joint with joint and separate with separate. Separately, all 13 real-checkpoint C++ Metal parity cases passed against the Python CPU oracle, including all 25 hidden-state outputs per case, under the unchanged `atol=rtol=3e-4` tolerance; the maximum hidden-state difference was `8.87e-5`. Both C++ backend CTest suites passed 6/6 tests after the Python benchmark merge, and the optional live Python/C++ CPU comparison passed. Matching benchmark logits alone would not prove intermediate-layer parity.

## Reproduce the workload

The native `gliner-bench` commands below remain supported. The temporary Python comparison harness has been removed from the current tree; its command below is a historical reproduction instruction for [revision 647ad73](https://github.com/sandrohanea/gliner.cpp/tree/647ad73), which preserves [tests/bench_python.py](https://github.com/sandrohanea/gliner.cpp/blob/647ad73/tests/bench_python.py) and its dependency instructions.

Build separate Release CPU and Metal executables and prepare the local checkpoint as described in the [main README](../../README.md#performance-benchmark). Run each command sequentially, with unrelated workloads stopped:

```sh
cmake -S . -B build-bench-cpu -DCMAKE_BUILD_TYPE=Release -DGGML_CUDA=OFF -DGGML_METAL=OFF
cmake --build build-bench-cpu -j
cmake -S . -B build-metal -DCMAKE_BUILD_TYPE=Release -DGGML_METAL=ON -DGLINER_GGML_SOURCE_DIR="$PWD/ggml"
cmake --build build-metal -j

build-bench-cpu/gliner-bench --model models/decide.gguf \
  --text 'Please refund my order; the delivery was late.' \
  --task intent --labels refund_request,order_status,other \
  --task sentiment --labels positive,neutral,negative \
  --threads 4 --mode both --warmup 3 --iterations 20 \
  > build-bench-cpu/bench-cpu-standard.json

build-metal/gliner-bench --model models/decide.gguf \
  --text 'Please refund my order; the delivery was late.' \
  --task intent --labels refund_request,order_status,other \
  --task sentiment --labels positive,neutral,negative \
  --threads 4 --mode both --warmup 3 --iterations 20 \
  > build-metal/bench-metal-standard.json

PYTHONPATH=models/python-deps TOKENIZERS_PARALLELISM=false \
  python tests/bench_python.py --checkpoint models/GLiNER2.5-Decide --device cpu \
  --text 'Please refund my order; the delivery was late.' \
  --task intent --labels refund_request,order_status,other \
  --task sentiment --labels positive,neutral,negative \
  --threads 4 --mode both --warmup 3 --iterations 20 \
  > build-bench-cpu/bench-python-cpu-standard.json
```

`PYTHONPATH=models/python-deps` reflects this machine's local dependency installation; use your own Python environment when reproducing. The ignored JSON files above contain all samples and final logits. Preserve them with the source revision and power/thermal conditions for follow-up runs.

## Interpretation and limits

- Python CPU's upstream tokenizer cache remains active across requests and modes; C++ currently has no matching cache. PyTorch's Accelerate-backed kernels and different execution path are other possible contributors. No component-level profiling was done.
- The Metal F32 shader overlay favors numerical parity and may affect throughput. These results do not compare it with GGML's original shader.
- Power was confirmed as AC after the measurements; a per-sample power or thermal log was not captured. The earlier Mac run used a different text/schema, so its timing change cannot be attributed to the charger.
- Twenty samples of one repeated short input do not establish sustained throughput or tail latency for longer contexts. Peak memory, concurrent requests and real-checkpoint F16 performance were not measured.
