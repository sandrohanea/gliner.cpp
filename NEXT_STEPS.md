# Next steps

## Implemented

- **Recorded benchmark reports:** [Windows CPU/CUDA and Python results](docs/benchmarks/2026-09-25-windows-rtx4060.md) and [M4 Pro CPU/Metal and Python results](docs/benchmarks/2026-09-25-macos-m4-pro.md) record measurements, versions, workload, methodology and limits. [The benchmark index](docs/benchmarks/README.md) lists separate device reports.
- **GGUF-only text classification:** C++ schema construction, Unicode word splitting/lowercasing, NFC/Metaspace Unigram tokenization, marker routing, DeBERTa embeddings and every encoder layer, and contextual classification.
- **Model-format validation:** application format version 2 preserves all tensors and carries required encoder/tokenizer behavior. Legacy files remain head-only; unsupported or incomplete new models fail explicitly.
- **C API and CLI:** `gliner_classify_text`, per-state diagnostics, `--text`/`--text-file`, prompts, descriptions, word truncation and explicit token limits. The precomputed `--states` path is retained.
- **Joint question batching:** `gliner_classify_text_batch` accepts one text and ordered tasks; CLI repeated `--task` groups expose per-question labels, prompts, descriptions and decoding. The model is loaded once, the text token sequence is included once, and all questions share one encoder pass. Task score ranges preserve grouping, while single-task behavior/output remains compatible. Joint scores can differ from independent calls because schemas attend to one another.
- **Grouped native span extraction:** `gliner_extract_spans` and `gliner-extract` score multiple described entity/keyphrase labels in one encoder pass using the preserved `markerV0` head, count gate and first `count_lstm` step. Results include verbatim text, UTF-8 byte offsets, raw logits and confidence, with per-label greedy overlap suppression and top-k. Reconvert to add validated span metadata; old GGUF classification remains supported. CPU upstream checks and synthetic F32/F16 coverage are in place. Decide's search-term quality is best-effort: the Cloudflare example did not produce the requested groups at the tested threshold in either implementation.
- **Count-conditioned repeated records:** `gliner_extract_records` and `gliner-extract --structure ... --field ...` use a fixed generic schema, predict 0..19 slots, and run the full learned positional/GRU conditioning for each slot. One encoder pass is followed by a head-only graph using device-resident features. List/single fields, per-slot overlap/top-k, raw count/slot logits and UTF-8 offsets are supported; all-empty records are omitted and max-record safety limits fail without truncation. CPU real-record parity and synthetic counts through 19 are covered. No retraining or checkpoint changes are implied; the Cloudflare `search_requests/terms` schema still needs quality work/fine-tuning.
- **Basic decoding:** exclusive softmax/argmax, independent sigmoid thresholds and probability temperature, with unmodified raw logits.
- **Parity:** committed synthetic token/hidden-state/logit fixtures and optional live checks against the real F32 Decide checkpoint. Eight single-task and five joint-schema cases match token IDs, routing and task offsets exactly. CPU maximum observed absolute hidden-state error is below `3e-5` for single tasks and `1e-4` for joint schemas across all 24 layers. All 13 real cases pass on an Apple M4 Pro Metal build with a maximum of `8.87e-5`; the user-reported RTX 4060 Laptop CUDA run also passes all 13 with a maximum of `0.00010967255`. Tolerances were unchanged. A C callback-count test verifies one encoder traversal per batch. See README for revisions and reproduction commands.
- **Model input APIs:** file, borrowed byte buffer and whisper-style sequential stream loaders (`read`/`eof`/`close`). Stream loading handles short reads without seeking, copying the entire checkpoint or creating a temporary file. Accepted loaders close exactly once on success/failure; input memory can be released after initialization.
- **Build-time backends (GPU paths experimental):** `GGML_CUDA`/`GGML_METAL` choose a fixed execution backend; both off selects CPU. No runtime backend/device selection parameters are exposed. Weights and state scratch use the compiled backend's first available device, graph matmuls request F32 accumulation and F32 activation inputs except in the explicit fast Metal build, and unsupported operations fail explicitly without silent fallback. Read-only `--build-info`, `--inspect` and `--debug` report build/runtime identity.
- **CUDA precision diagnosis:** the user-reported RTX 4060 Laptop GPU synthetic suite passes with `NVIDIA_TF32_OVERRIDE=0`, while default cuBLAS TF32 math exceeded an F32 golden tolerance. CUDA parity runners now explicitly disable TF32 and select F32 cuBLAS computation, without loosening tolerances. Normal inference needs the same launch environment; the library does not mutate process-wide settings.
- **Short-sequence CUDA precision fix (hardware-confirmed):** the 12-token case exposed GGML's separate TF32 MMF kernel. Graphs now request F32 activation inputs as well as accumulation; a build-directory source overlay makes the pinned CUDA dispatch honor that request without modifying the GGML checkout. On 2026-09-25, the user reported all 13 real F32 cases passing on Windows with an RTX 4060 Laptop GPU (compute capability 8.9, 8187 MiB VRAM, VMM enabled), using `NVIDIA_TF32_OVERRIDE=0` and `GGML_CUDA_CUBLAS_COMPUTE_TYPE=f32`. All 25 hidden-state outputs and final scores/decisions pass the existing `atol=rtol=3e-4` checks. The rebuilt binary also passed all three expanded CTest tests, including the 32-wide short/long synthetic goldens. Recorded versions: CUDA 13.4 / nvcc V13.4.59, NVIDIA Windows driver `32.0.15.9155`, gliner.cpp `ee9c8a495c224c4fb9b0aab2ca61f1bb0af09765`, GGML `456172ec733a135778adcd32d00e576a58232e45`. CUDA builds temporarily require local/fetched GGML source.
- **Persistent-model benchmark:** `gliner-bench` uses the shared C API on the build's CPU/CUDA/Metal backend. It loads weights once and reuses states, measuring load/state-init/first-request time separately from warmup and steady-state samples. JSON reports raw samples, median/p95, request/question throughput, actual token counts and joint versus separate modes. The [Windows report](docs/benchmarks/2026-09-25-windows-rtx4060.md) and [M4 Pro report](docs/benchmarks/2026-09-25-macos-m4-pro.md) record the same two-task workload on each device, including C++ CPU/GPU and Python CPU results. These are repeated short workloads, not general performance guarantees; peak-memory telemetry remains outstanding.
- **Lean developer tooling:** the exploratory Python performance harness/tests and redundant label-state exporter are removed; their measured comparisons remain in the device reports with historical-harness links. CUDA/Metal overlay checks now run as native CMake tests. The remaining Python is limited to the streaming converter, standard-library synthetic/CLI tests and one optional upstream parity/golden-generation tool. `GLINER_PYTHON_TESTS=OFF` disables Python test discovery without changing runtime behavior; see [testing documentation](docs/testing.md).
- **Metal F32 precision fix and hardware parity:** pinned GGML's F32 matrix-matrix shader narrows both operands to F16, causing the original 165-token synthetic case to fail at layer 1. By default, a build-directory overlay routes F32×F32 products requesting F32 accumulation to GGML's F32 matrix-vector shader. The GGML checkout stays unchanged; strict Metal builds require source. On an Apple M4 Pro, F32/F16 synthetic conversion tests and all 13 real F32 parity cases pass without tolerance changes. `GLINER_METAL_STRICT_F32=OFF` selects stock dispatch and skips graph precision requests for faster inference; it fails strict synthetic F32 parity, so fast-build CTest retains conversion/API checks without claiming encoder parity.

## Remaining

1. **CUDA benchmarking and broader coverage (priority).** All 13 real F32 cases and the expanded synthetic suite now pass on the user's Windows RTX 4060 Laptop GPU with CUDA 13.4.59. Use `gliner-bench` on identical CPU/CUDA workloads to compare model loading and median/p95 warm inference, including joint/separate questions and different token lengths. Add peak-RAM/VRAM telemetry; file size is not a substitute. Repeat correctness checks on Linux and other GPUs. Test concurrent states sharing weights, allocation failures and longer sequences. Establish real-checkpoint F16 error budgets before enabling reduced-precision optimizations or extending the F32 parity claim. Replace the source overlay and process-wide TF32 override with upstream precision controls when available.
2. **Broader Metal validation and optimization (priority).** Repeat the F32 parity suite on other Apple GPUs and macOS/toolchain versions. Establish real-checkpoint F16 error budgets, exercise memory pressure and longer sequences, and benchmark more token lengths and schema sizes against CPU and the default GGML shader. Measure peak memory and repeat cold loading under controlled cache conditions before generalizing the short-workload speedup.
3. **Backend memory management and coverage.** Evaluate build-configured GGML scheduler-based CPU fallback/partial offload with explicit placement reporting when a device lacks an op or sufficient memory. Keep backend selection at build time and avoid silent fallback. Evaluate pinned transfers for CUDA and unified-memory placement for Metal; consider Vulkan and other GGML backends only after CUDA/Metal acceptance gates. Multi-GPU splitting is a separate future milestone.
4. **Broader parity and extraction quality.** Run the entity and recurrent record graphs on CUDA and strict Metal; classification parity alone does not validate them. Build a held-out retrieval-request corpus annotated with grouped term spans, including zero-request examples, then evaluate fine-tuning the encoder/span/count/conditioning heads. Preserve request membership and avoid training only flat keywords. Evaluate extraction-focused checkpoints before promising specific search terms. Add longer contexts and real-checkpoint F16 tests while preserving raw-logit parity.
5. **Upstream schema/decision surface.** Add few-shot examples, explicit description ordering independent of label order, cross-task constraints and upstream exact/beam decoding. Multiple tasks per encoder pass are implemented; constrained decisions are not. Match upstream decisions and tie-breaking before claiming full Python API parity.
6. **Long documents and multi-document batching.** Add explicit overlapping-window extraction with original offsets and cross-window deduplication, then variable-length document batches and attention masks. Current extraction is bounded by the aggregate token budget and checkpoint span width (8 word/punctuation tokens for Decide). Joint classification shares one text across questions, not multiple independent documents. Limits deliberately fail rather than silently chunking or dropping input.
7. **Performance.** Repeat longer, isolated runs and profile the observed PyTorch mean-latency advantage on CPU and the measured GPU backends before choosing optimizations. Compare CPU matrix kernels/threading, GPU kernel/launch and transfer costs, graph construction, and tokenizer-cache behavior. Preserve F32 precision fixes and tolerances. Add automated workload sweeps and result-file comparisons. Use measured bottlenecks to prioritize reducing attention-index memory, precomputing immutable relative projections, memory mapping and schema tokenization caches. Use CPU/CUDA/Metal parity gates when changing graph layouts or kernels.
8. **Quantization and packaging.** Establish separate error budgets for F16 and quantized weights; retain original tensors unless a new format version explicitly documents pruning. Add install/export targets and platform CI with installed GGML for CPU, local/fetched GGML for GPU, plus NVIDIA CUDA and Apple Silicon Metal hardware lanes.

CUDA has user-reported real-checkpoint F32 parity for all 13 cases on the Windows RTX 4060 Laptop GPU under the documented precision settings. Metal F32 parity is verified on an Apple M4 Pro. Real-checkpoint F16 and broader hardware/performance validation remain pending. Run CTest in separate CPU/CUDA/Metal build directories; each suite asserts its binary's compiled backend and unavailable GPU devices fail rather than skip. CPU remains the reference inference path.

Grouped entity/keyphrase spans and one repeated-record schema with list/single extractive fields are supported. Nested/choice-field/relation extraction, generated search-query terms, multiple or mixed schema types in one call and alternate encoders remain outside the current runtime.
